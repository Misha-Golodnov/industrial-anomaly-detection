# Процесс эксплуатации модели: анализ нового прогона

Версия 1.0. Дата: 08.11.2026. Статус: проектируемая пакетная эксплуатация исследовательского прототипа.

## Цель и границы

Проанализировать новый файл показаний установки, зарегистрировать отклонения от нормы и передать тревогу инженеру для решения. Один экземпляр процесса соответствует одному файлу / партии данных. Процесс не является программой управления установкой и не выполняет автоматическое аварийное отключение.

В репозитории уже есть подготовка окон, статистические детекторы и офлайн-оценка. Сохранение и загрузка утверждённого пакета модели, эксплуатационный журнал, уведомления и пользовательские задачи инженера на диаграмме являются целевыми шагами, а не заявлением о наличии готового сервиса. Схема описательная: isExecutable=false; импорт в BPMN-редактор не запускает процесс.

## Участники

Один пул «Мониторинг состояния установки» содержит три дорожки:

- Модуль подготовки данных: принимает файл и проверяет данные.
- Модуль детекции: применяет готовую модель и сохраняет результаты.
- Инженер / оператор: проверяет тревогу и документирует решение.

## Предусловия и вход

До поступления файла утверждён и доступен единый пакет: порядок 52 каналов, скейлер, обученное состояние трёх детекторов, нормировочные квантили, центр/масштаб EWMA, lam=0.2, полный порог и идентификатор версии. Обучение и согласование новой версии - отдельный процесс. Округлённый порог 1.866 из сохранённой строки отчёта не заменяет точное значение.

На входе - показания 52 каналов, идентификатор прогона и упорядоченные временные отсчёты. Проверяются обязательные поля, конечность чисел, дубликаты/пропуски в сетке и наличие хотя бы 24 отсчётов. Для разных прогонов окна не смешиваются. Истинный момент начала неисправности при эксплуатации неизвестен; правило исключения окон вокруг 161-го отсчёта из тестового эксперимента здесь не применяется.

## Основной сценарий

1. Стартовое событие: получен файл.
2. Автоматическая задача: проверить структуру и качество данных.
3. Исключающий шлюз «Данные корректны и достаточны?»: при ответе «Нет» записать проблему и закончить с исходом «Данные отклонены».
4. При ответе «Да»: применить сохранённый скейлер и построить окна 24 x 52 с шагом 8.
5. Рассчитать скоры готовой моделью; внутри партии упорядочить окна по времени и сбросить EWMA на границе каждого прогона. Для текущего API использовать score_batch с метаданными. При делении одного прогона на несколько запросов потребуется отдельная реализация переноса состояния, которой эта схема не приписывает текущему коду.
6. Сохранить скоры, границы окон, точный порог и версию модели.
7. Исключающий шлюз «Есть превышение порога?»: если ни одно окно не имеет score >= threshold, завершить с исходом «Отчёт сохранён; тревог нет».
8. При превышении сформировать тревогу с перечнем подозрительных окон и передать её инженеру. Способ доставки и норматив реакции ещё не определены.
9. Пользовательская задача: инженер проверяет показания, контекст и возможные проблемы измерений.
10. Исключающий шлюз «Проблема подтверждена?»: при «Да» зарегистрировать инцидент и передать его на обслуживание по действующему регламенту; при «Нет» зарегистрировать ложную тревогу. Обе ветви документируют решение инженера и заканчиваются исходом «Проверка завершена».

## Техническое исключение

Прерывающее пограничное Error Event прикреплено к задаче расчёта. При невозможности загрузить/применить модель, неверной форме результата, NaN или другой ошибке выполняется отдельная ветвь: зарегистрировать ошибку и уведомить инженера; закончить с исходом «Расчёт не выполнен». Такой файл не считается нормальным и не входит в результат «Тревог нет».

## Выходы и аудит

Для каждой партии сохраняются идентификатор входа, версия пакета, время обработки, идентификаторы прогонов, границы окон, скоры, порог и исход обработки. Для тревог дополнительно сохраняются решение инженера, обоснование и ссылка на инцидент или отметка ложного срабатывания. ФИО конкретных исполнителей, SLA и система заявок в проекте не зафиксированы и не выдумываются в документации.

Оценка обратной связи может инициировать отдельный согласуемый процесс дообучения/перекалибровки. Автоматически менять порог по каждому новому файлу не предполагается.

## Нотация и редактирование

Исходник model_operation.bpmn содержит BPMN 2.0 XML и BPMNDI (координаты). Service Task обозначает автоматическую задачу, User Task - действие инженера. Все ромбы являются XOR-шлюзами. Сплошные стрелки - Sequence Flow внутри одного пула; пунктирные связи показывают используемый пакет данных модели. Схема использует один пул, поэтому Message Flow между пулами отсутствует.

Открывайте .bpmn в совместимом BPMN-редакторе. SVG, PNG и PDF предоставлены для просмотра, а не вместо редактируемого исходника. В SVG/PDF добавлены заголовок и пояснения; бизнес-узлы, ветвления и дорожки соответствуют XML.

Источники: [OMG BPMN 2.0.2](https://www.omg.org/spec/BPMN/2.0.2), MODEL_CARD.md, код проекта версии 42f3a27.
