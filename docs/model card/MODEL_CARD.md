# Model Card: TEP Novelty Detector

Версия документа 1.0 | 08.11.2026

## 1. Model Details / Сведения о модели

TEP Novelty Detector — исследовательская модель для одноклассового поиска новизны в многомерных временных рядах промышленного технологического процесса Tennessee Eastman Process (TEP). Модель предназначена для обнаружения отклонений от нормального режима работы оборудования без использования примеров неисправностей при обучении.
В качестве основной архитектуры используется составная модель TailMax + WithinRunEWMA, объединяющая три детектора: CanonicalVariateIndex, WindowMomentIndex и SlowFeatureIndex.

CanonicalVariateIndex анализирует взаимосвязи между первой и второй половинами временного окна. WindowMomentIndex оценивает статистические характеристики сигналов с учётом их ковариации, а SlowFeatureIndex выделяет медленно изменяющиеся компоненты многомерных временных рядов. Полученные оценки аномальности нормируются и объединяются методом TailMax, после чего сглаживаются экспоненциальным скользящим средним WithinRunEWMA с коэффициентом λ = 0,2.

## 2. Intended Use / Назначение

Основное применение - диагностика инженерных систем при помощи ИИ, исследование и сравнение методов поиска новизны на TEP.



## 3. Factors / Влияющие факторы и контракт входа

Ключевые факторы: тип отказа, режим установки, каналы, длина/шаг окна, пропуски, порядок отсчётов, границы прогонов и останов установки.

Вход: окна float32 формы (n, 24, 52), каналы xmeas_1..41, затем xmv_1..11; шаг 8. Исходная сетка времени - 3 минуты. Выход: один конечный скор на окно и тревога при score >= threshold. Для корректного EWMA необходимы simulation_run и sample_end; состояние сбрасывается между прогонами.

## 4. Metrics / Метрики и правило решения

| Показатель           | Как трактовать                                                                    |
|----------------------|-----------------------------------------------------------------------------------|
| normal_test_fpr      | доля ложных тревог среди нормальных окон.                                         |
| false_alarm_run_rate | доля нормальных тестовых прогонов хотя бы с одной тревогой.                       |
| detection rate       | доля обнаруженных неисправных прогонов.                                           |
| early_detection_rate | доля прогонов с обнаружением на первом допустимом окне.                           |
| median_delay_minutes | средняя задержка первого обнаружения.                                             |
| AUCROC               | Ранжирование оценок допустимых окон отказа относительно нормальных тестовых окон. |


threshold_at_fpr выбирает порог по нормальным валидационным окнам с целевой долей тревог не выше 0.01. В сохранённой строке отчёта порог финальной сборки округлён до 1.866. Полное значение порога и обученное состояние в отдельном проверенном артефакте не представлены; округлённое число нельзя подставлять вместо воспроизводимой калибровки.

## 5. Evaluation Data / Данные и протокол оценки

Нормальный тест: TEP_FaultFree_Testing.RData. Неисправный тест: TEP_Faulty_Testing.RData, 20 типов неисправностей. Источник - расширенные симуляции Rieth et al. (2017). Тестовые неисправности используются для расчёта качества, а не для fit компонентов или выбора порога.

- Отказ в тестовой разметке начинается с отсчёта 161. Смешанные окна, содержащие норму и отказ, исключаются.

- Остановка отмечается по первому xmeas_7 >= 2990 кПа. Окна, целиком начинающиеся после этой точки, исключаются из оценки обнаружения. Пересекающее останов окно код может учитывать - полного отсечения всех таких окон нет.

- Первое целиком неисправное окно имеет границы 161..184. Минимальная засчитываемая задержка равна (184 - 160) * 3 = 72 минуты. Это свойство тестового протокола, а не измеренный SLA сервиса.

## 8. Ethical Considerations / Последствия применения

- Пропуск неисправности может задержать реакцию инженера. Низкий скор не подтверждает безопасность установки.

- Частые ложные тревоги увеличивают нагрузку и могут вызывать привыкание к уведомлениям. Наблюдавшиеся 30.2% нормальных прогонов с тревогой требуют явного учёта при проектировании процесса.

- В предложенной эксплуатации модель поддерживает решение инженера. Подтверждение причины и действия по регламенту остаются у ответственного специалиста; автоматическая остановка моделью не предусмотрена.

- Данные симуляционные; персональные данные в рассмотренных признаках не представлены. При переносе на реальные архивы нужны отдельные правила доступа и защиты технологических данных.

## 9. Caveats and Recommendations / Ограничения и рекомендации


- В тексте эксперимента варианты сравниваются на полном тесте и по этим результатам выбирается сборка. Это исследовательская оценка с риском подбора под тест. Для финального подтверждения нужна заранее зафиксированная конфигурация и ранее неиспользовавшиеся данные.

- Границы отказа 161 и признаки post_shutdown относятся к офлайн-оценке. В эксплуатации истинное время начала отказа неизвестно: окна нельзя отбрасывать на основании будущих меток.

- score(batch.X) считает всю пачку одним прогоном. Для данных нескольких прогонов нужен score_batch с метаданными. Пакетный интерфейс сбрасывает EWMA при каждом вызове; потоковый сервис с памятью между отдельными запросами в текущем проекте не подтверждён.

- Свёрточный кандидат использует собственную модификацию идей MiniRocket/MultiRocket. Его результаты не являются оценкой всех оригинальных реализаций этих методов.

- Перед эксплуатацией сохранять и версионировать как единый пакет порядок каналов, скейлер, состояние трёх детекторов, квантили, центр/масштаб EWMA, lam и точный порог. Проверять формат и конечность входа, вести журнал ошибок и подтверждений инженера. Переобучение и изменение порога - отдельная согласуемая процедура.

Проверка воспроизводимости: восстановить окружение из poetry.lock, использовать зафиксированный коммит и исходные RData, последовательно выполнить 03_fused_index.ipynb. Аппаратная конфигурация и время обучения не рассматриваются как измеренные характеристики эксплуатации.
